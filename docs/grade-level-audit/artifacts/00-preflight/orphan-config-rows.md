## How orphans accumulate

Per the code-trace agent finding for [schools.service.ts:884-887](../../../server/application/microservices/identity/src/schools/schools.service.ts#L884-L887):

```ts
async getConfiguration(schoolId, context) {
  const config = await this.queryConfig(EntityKeyBuilder.schoolConfig(schoolId));
  if (!config) {
    return await this.createDefaultConfig(schoolId, context);  // ← writes new row from DEFAULT_SCHOOL_CONFIG (US defaults)
  }
  return config;
}
```

When the frontend prefetches `GET /api/schools/<schoolId>/configuration` for a `schoolId` that was generated by a wizard but never finished a `POST /api/schools` (operator clicked Cancel, browser closed, network error, etc.), this lazy fallback fires and **writes a US-defaults row to a non-existent school**. The row stays forever; nothing ever GCs it.

Two orphan rows accumulated in one short operator session on a fresh dev tenant. At scale (multi-tenant production with many operators), this grows monotonically.

## Why it didn't bite School A

The **eager** path at [SchoolsService.createSchool line ~297-313](../../../server/application/microservices/identity/src/schools/schools.service.ts#L297) runs `getDefaultConfigForCountry(countryCode)` and merges `COUNTRY_CONFIG_OVERRIDES['NPL']` BEFORE writing. This produces correct PABSON-merged values, which is what School A's row carries.

The **lazy** path bypasses the country merge entirely. So real schools get correct configs; orphan/abandoned schoolIds get US-defaults configs.

## Severity

- **Live consumers** ([sections.service.ts:177](../../../server/application/microservices/academics/src/sections/sections.service.ts#L177), [grades.service.ts:604+](../../../server/application/microservices/academics/src/grades/grades.service.ts#L604)) read by `(tenantId, schoolId)`. If they query for a real school, they get the correct config. If they somehow query for an orphan schoolId, they get US defaults — but no production code path queries non-existent school IDs.
- **Data hygiene impact:** orphan rows accumulate; storage cost is trivial; auditability is harmed (a future compliance grep would surface "evidence" of US-defaults rows in a Nepal-only tenant).
- **Lazy fallback is actively writing wrong data to DDB** for any GET against a non-existent school. This is a side-effect-on-read pattern that's hostile to caching and idempotency.

## Fix

Two-pronged. Both small.

1. **Code fix** — remove the lazy `createDefaultConfig` fallback. Return 404 when school doesn't exist. Configurations should ONLY be created by the eager path during `createSchool`. Estimated effort: S.
2. **Data fix** — one-shot DDB scan + delete for orphan `#CONFIG` rows in every tenant. Pre-flight: count orphans per tenant; the audit run on dev-pabson-primary suggests low single digits per tenant. Estimated effort: S (one-time script, read-only audit + targeted deletes).

Track as **F-CONFIG-2**. Bundle with **F-CONFIG-1a** (fix the lazy fallback path itself) into one PR.
